# journal · 每日记录口径

数据链路：`npm run journal:sync` 出草稿 → 用户审 → `npm run journal:accept` 落 `daily.json`（入 git）。
草稿在 `.inbox/`（已 gitignore），未经审核不进仓库、不上页面。

## 每日条目怎么压（2026-11-20 用户定规）

- **站点 2–3 条**：只留结构与决策，纯样式微调并进它所属的那条。当天没有站点改造 → 该组不显示。
- **内容 ≤5 条**：同一篇的「新增 / 改标题 / 调口径」合成一条。
- **产线 1–3 条**：写内容层产出（哪一集、讲什么、交付到什么程度），不写组件名与函数名。
- **文档 / 工程 0–1 条**：只有合规、部署、CI 这类才单列。
- **里程碑**单独一行。
- 每条附「N 提交」用于追溯，页面上不显示。
- 英文提交摘要必须译成中文，未译不进库（`accept.mjs` 有闸门）。

## 一件事怎么写成一条

先问「这条读起来有没有信息」，没有就并进相邻那条。判断标准：

- 写了决策（换什么、为什么换）→ 留
- 只写了「改了某处样式」→ 并进所属主题
- 一天里 6 成提交是同一主题的连续微调 → 并成一条，标提交数

## 数据边界

- 三仓库：`site/XiaoBlog`（站点）、`engine`（产线）、`text2Media`（产线）。
- 判断、失误、线下活动、收入、反馈 git 里没有，写在 `activity.md` 的 `## YYYY-MM-DD` 段里，带 `[判断][失误][活动][反馈][收入]` 标签。
- 里程碑写 `milestones.md`。

## 文案规范（2026-11-20 用户批准）

1. **主题句**：不超过 16 字的口语判断，写那天真正发生的事，不写任务名。
   - 反例 `把版式定下来`（任务名）→ 正例 `版式定死，第一篇也发出去了`
2. **每日一句（summary）**：一句有底气/有收获的话，不超过 30 字；页面上是卡片的视觉落点（15px 引文式）。
   - 例 `今天最实在的一件事，是第一次有了「不用再改」的底气。`
3. **条目标题**：拆成「主句；细节」。主句 = 动作 + 结果，不超过 26 字；技术细节降格到「；」之后的小字。
   - 反例 `全站统一到 graphite + 高亮笔设计系统，落 C 杂志式排版并整体降一档字号`
   - 正例 `一套绿灰配色和字号定死，往后每页照抄；graphite + 高亮笔设计系统，C 杂志式排版，正文收到 15px`
4. commit 原文与 hashes 全部留在 daily.json 里追溯，页面只显示改写后的句子。

## 页面展示规则（2026-11-20）

- **分组顺序固定为 内容 → 产线 → 文档 → 站点**：内容是重点，站点是施工日志，排最后。不依赖 json 的 items 顺序。
- **默认只展开最近一天**：今天有记录就展开今天，没有就退到有记录的那一天；其余日子压成一行折叠条（主题 · 提交数 · 展开），仍挂在同一条时间脊柱上，空心圆点表示折叠。
- 右上角「全部展开 / 只看最近一天」一键切换；单张卡片右上角有「收起」。
- **阶段分段（2026-11-20 已落地）**：记录按四阶段分组，当前阶段整段展开（组内仍只展开最近一天），已结束阶段与筹备期整段压成一行（阶段 · 名称 · 日期区间 · N 天记录 · N 提交 · 展开），点组头才展开该阶段所有日期；「全部展开 / 只看最近」一键在两级之间切换。
