部署这类事我经常干，复杂的商用系统也部署过不少，只是以前都得自己一条条敲命令、自己写脚本。这回在阿里云上试了它的自然语言交互，想看看能不能把这些活儿交出去。

我给自己定的目标是：一台全新的 ECS，从零开始，最后做到提交代码后自动构建、自动上线，用公网 IP 就能打开。整个过程大概一个小时。中间来回交互了很多轮，远不是一句话的事。

## 装环境

我先让它把环境准备好。它自己看了下系统，是 Alibaba Cloud Linux 3，按这个发行版选了装法，几条命令搞定，然后 Git、Node.js 20 和 npm 的版本都核对了一遍。这一步没卡。

## 克隆和构建

接着把仓库地址给它，让它克隆下来，构建到 `/opt/XiaoBlog/dist`。

中间撞上了 git 的 `safe.directory` 报错。这个报错我以前碰到过，每次都得先搜一下才知道怎么绕。这回它自己就修了，最终构建出 34 个页面。

## Nginx：配置对了，页面还是默认页

我说把 `dist` 挂到 80 端口，公网 IP 能访问。它写好配置、测了语法、重载服务，每一步都报了结果。

结果我一打开，还是 Nginx 的默认欢迎页。

原因是主配置里自带的默认 server 块盖住了我的站点——`default_server` 先匹配，我那份配置在后面，压根没轮到。它把那段注释掉，重载，再请求，200。

这类坑最典型：配置本身没错，语法检查也过，错的是它在整个配置体系里的位置。

## CI/CD：烦躁的都在这儿

我想要的是：提交代码后，GitHub Actions 自动 SSH 上服务器，拉代码、构建、部署。

AI 给的方案是：建一个专用的 deployer 用户，生成一对 SSH 密钥，sudo 只放行 reload nginx 这一条，再写服务端的部署脚本和 workflow 文件。每一步它都会先说一句要干什么，再动手。

然后就卡在 SSH 认证上了。Actions 一直报 `Permission denied (publickey)`，前后折腾了四轮：

1. 直接把 OpenSSH 格式的私钥放进 Secret。失败。它判断是格式兼容问题。
2. 改成 Base64 编码，配合 `key_path` 参数。还是失败。这次它怀疑是 `appleboy/ssh-action` 解析 OpenSSH 格式有问题。
3. 干脆不用这个 action，换成原生 `ssh` 命令。依旧失败。这回查出来 `authorized_keys` 里留着之前试错时的旧密钥，把事情搅乱了。
4. 新建 deployer 用户，重新生成独立密钥，Base64 编码，用原生 `ssh`。通了。

说实话，这一步我是真的烦。要不是卡在这里，整个部署半小时就能收尾，光 SSH 认证就吃掉了差不多一半时间。

不过冷静想想，如果是我自己做，也一样会烦，而且多半就是打开浏览器到处查资料、一个个排查，不会比这更快。

至少这次每一轮失败它都会说清楚原因，以及下一步准备改什么，没有在同一个坑里反复打转。这一点比我自己的排查过程要干净。

## 验证

我让它验证整条链路。它触发了一次 Actions，等跑完，用 `curl` 请求，拿到 200，页面内容和本地构建的一致。

到这儿闭环了。最后我让它把这次过程写成文章，这篇的初稿就是这么来的。

## 说说感受

最让我意外的是自然语言交互本身。以前这类事我都得自己写脚本，又费劲又零碎。现在我只要说清楚想要什么，剩下的命令、配置、排错它来处理，我在旁边确认和授权就行。

我自己部署经验多，它在做什么我大致看得懂。但我觉得对不懂技术的人来说，这条路也走得通，门槛比以前低太多了。

不过我想说的不止是部署。我认为，自然语言交互是改造现有系统的第一步。这个判断我今年年初就确认过了，但现在还有很多人没意识到。

我自己做过一个自然语言交互的 CRM，管进销存。用户直接输入「张三来买了一包烟」，系统会把信息都提取出来，生成一张确认卡片，用户看一眼，点确认就行。以前的流程是：打开新增销售记录的页面，一个字段一个字段地填，再保存。现在是一句话，加一次点击。

这个案例我会放到后面的洞察系列文章里细讲。

至于这个博客，现在就跑在那台服务器上，每次提交代码都会自动上线。
