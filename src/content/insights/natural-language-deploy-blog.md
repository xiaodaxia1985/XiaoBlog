部署这类事我经常干，复杂的商用系统也部署过不少，以前都是自己一条条敲命令、自己写脚本。这次在阿里云上试了它的自然语言交互，想看看能不能把这些活交出去。

我定的目标很具体：一台全新的 ECS，从零开始，提交代码后自动上线，用公网 IP 就能打开。整个过程大约一个小时，中间来回了很多轮，远不是一句话的事。

## 装环境

我先让它把环境准备好。它自己看了系统，是 Alibaba Cloud Linux 3，就按这个发行版选了安装方式，几条命令装完，再把 Git、Node.js 20 和 npm 的版本逐个核对了一遍。

## 克隆和构建

接着把仓库地址给它，让它克隆下来，构建到 `/opt/XiaoBlog/dist`。

构建时撞上了 git 的 `safe.directory` 报错。这个报错我以前碰到过，每次都得先搜一下才知道怎么绕。这回它自己判断了原因，自己修好，最终成功构建。

## Nginx：配置对了，页面还是默认页

我说把 `dist` 挂到 80 端口，让公网 IP 能访问。它写好配置、测了语法、重载服务，每一步都报了结果。

打开一看，还是 Nginx 的默认欢迎页。

原因在主配置里：自带的默认 server 块设了 `default_server`，先匹配，把我的站点盖住了。我那份配置排在后面，根本没有轮到。它把那段注释掉，重载，再请求，返回 200。

## CI/CD：烦躁的都在这儿

我想要的是：提交代码后，GitHub Actions 自动 SSH 上服务器，拉代码、构建、部署。

它给的方案是：建一个专用的 deployer 用户，生成一对 SSH 密钥，sudo 只放行 reload nginx 这一条，再写服务端的部署脚本和 workflow 文件。每一步它都先说一句要干什么，再动手。

然后就卡在 SSH 认证上了。Actions 一直报 `Permission denied (publickey)`，前后试了四轮：

1. 直接把 OpenSSH 格式的私钥放进 Secret，失败。它判断是格式兼容问题。
2. 改成 Base64 编码，配合 `key_path` 参数，还是失败。它怀疑是 `appleboy/ssh-action` 解析 OpenSSH 格式有问题。
3. 不再用这个 action，换成原生 `ssh` 命令，依旧失败。这回查出 `authorized_keys` 里还留着之前试错时的旧密钥，把情况搅乱了。
4. 新建 deployer 用户，重新生成独立密钥，Base64 编码，用原生 `ssh`，通了。

说实话，这一步我是真的烦。但烦的不是它慢，是这一环本身就不顺。换我自己来做，也一样要去查资料、一个一个试，进度不会更快。

SSH 认证这一环用了约 30 分钟。要不是卡在这里，半小时就能收尾。

每一轮失败它都会说清楚原因，以及下一步准备改什么，没有在同一个坑里反复打转。

## 验证

我让它验证整条链路。它触发了一次 Actions，等跑完，用 `curl` 请求，拿到 200，页面内容和本地构建的一致。

到这里闭环了。这篇文章的初稿，也是我让它把这次过程整理出来的。

## 说说感受

最让我意外的是运维部署通过自然语言交互就能实现。以前这类事我得自己写脚本，又费劲又零碎。现在我只要说清楚想要什么，剩下的命令、配置、排错它来处理，我在旁边确认和授权就行。

具体省在哪儿：每一步它先说一句要干什么，再动手；报错它自己判断原因、自己改，不把一堆日志甩给我；我全程没有来回切浏览器查文档、抄命令。这一个小时里，我说得最多的是「可以」和「接着来」。

我有运维底子，能看懂它在做什么。它把实现路径规划好，然后落地执行。对不懂运维的人来说，这条路更值得说。我没有让完全零基础的人试过，这个结论只能说到这里。但你说清楚要什么结果，它把路径铺出来，卡住了它接着排，这一个小时里真正需要我自己动手解决的地方，几乎没有。

我想说的不止是部署。我认为，自然语言交互是改造现有系统的第一步。这个判断我今年年初就形成了：结合 AI 的发展来看，市面上有大量 SaaS 软件需要改造，而这一步投入不大，却可能见到很大的效果。这仍然是我的判断，还需要更多的验证。

我自己做过一个自然语言交互的 CRM，管进销存。用户直接输入「张三来买了一包烟」，系统把信息都提取出来，生成一张确认卡片，用户看一眼，点确认就行。以前的流程是：打开新增销售记录的页面，一个字段一个字段地填，再保存。现在是一句话，加一次点击。

这个案例我会放到后面的洞察系列文章里细讲。

这个项目现在就跑在那台服务器上，每次提交代码都会自动抓取代码、编译、部署上线。
