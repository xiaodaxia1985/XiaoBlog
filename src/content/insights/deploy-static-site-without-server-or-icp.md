我想先验证一件事能不能成立，需要一个能发给别人看的地址。不是一次性演示，得是能长期打开、能被搜索结果收录，还能贴进自己介绍里的那种地址。

需求很窄：一个静态站点、一个自己的域名、大陆能打开、不买服务器、不备案。下面是我实际走过的路径，包括中间走不通的那一段。

先说清楚范围：这套办法是我在境内做小范围验证、自测和给自己人看的时候用的，不是长期运营方案。读者用它要遵守所在地和中国大陆的法律法规，以及各平台自己的规则；我本人也不建议把它用在面向公众的经营性服务上。理由写在后面，不是免责声明式的客气话。

## 起因：先要一个能打开的地址

站点本身是纯静态的。用 Astro 搭，内容放在 Markdown 里，`npm run build` 产出 `dist` 目录，里面就是全部 HTML、CSS、图片和字体，没有任何后端逻辑，没有数据库，也没有需要常驻运行的进程。

这一点决定了后面所有选择：静态站不需要服务器，只需要有人把这些文件放到能公网访问的地方，给出一个连接，大家都能访问。

代码放在 GitHub 私有仓库里，本地在 `site/XiaoBlog`。构建通过，预览正常，剩下的问题只有一个：把它放到公网，并且绑上域名： `xiaomaker.top`。

## 第一站：Cloudflare 部署成功，但访问受限

第一个想到的是 Cloudflare。账户里建项目、连仓库、填构建命令，构建和部署都是成功的，站点在平台分配的默认子域名上能正常打开，页面上线了。

<img src="/images/cloudflare-workers-subdomain.webp" alt="Cloudflare 部署成功后分配的默认子域名，站点在该地址上正常打开" style="max-width:100%;height:auto" width="1360" height="775" loading="lazy" decoding="async">

地址栏里这个 `*.workers.dev` 就是部署成功后直接给的访问地址，不需要事先买域名。站点能打开，说明代码、构建和产物都没有问题。

部署没有问题，卡住的是可达性。用国内宽带打开，页面加载不出来。换手机蜂窝数据再试，同样打不开。问题不在某条线路偶尔抽风，而是不同地区和平台所遵循的法律法规不一样。

对一个要发给用户看的站点来说，这是致命的。站点做得再正确，打不开就等于不存在。所以我没继续在这条路上研究怎么优化，因为矛盾不在配置层。

## 第二站：EdgeOne Pages 上线了

第二个试的是腾讯云 EdgeOne Pages，现在控制台里叫 EdgeOne Makers。流程和大多数静态托管平台一致：授权 GitHub、选仓库、填构建命令与输出目录，然后等构建。

填的是 Astro 的默认值：

- 构建命令：`npm run build`

- 输出目录：`dist`

- Node 版本：跟本地一致

<img src="/images/edgeone-build-log.webp" alt="EdgeOne 构建日志：初始化、克隆仓库、安装依赖、构建、部署五个阶段均显示完成" style="max-width:100%;height:auto" width="1360" height="713" loading="lazy" decoding="async">

构建日志里五个阶段全部完成，最后一步是部署，耗时几十秒。构建通过、部署成功，平台会给一个默认域名（形如 `xxx.edgeone.app`）。

这个默认域名在大陆是预览性质：**有有效期限制，而且期限并不固定**，有时能维持较长时间，有时很短，以控制台当下的显示为准。它适合用来确认「站点真的跑起来了」，不能当作长期稳定的对外地址。要长期用，必须绑自己的域名。

到这里，技术上最难的部分其实已经结束了。真正卡住我的是下一步。

## 平台免费不等于能被看见

两个平台都不额外收托管费，就能把站点发出去，但给出的东西不是一回事。

Cloudflare 部署完成后直接给一个默认子域名，长期可用，不需要先买域名。这一点它做得很干净。问题只有一个：那个地址在网络受限地区打不开。

EdgeOne 也会给 `*.edgeone.app` 的默认域名，但它是预览性质，有有效期，而且期限并不固定。到期后这个地址就不能访问了。控制台里不会给你「这个地址永远属于你」的承诺，所以我必须绑自己的域名。

关键差别是：一个是可以长期依赖的地址，一个是随时可能失效的临时入口。

**这条路上真正的大头不是托管费，而是你在一个没人看得见的地方做验证。** 域名花了十几块钱，把站点发出去很容易，让目标读者能打开才是难点。

## 卡点：备案是接入制，不是域名制

在 EdgeOne 里给项目添加自定义域名时，要先选加速区域。这里的分叉很清楚：

- 选「中国大陆」或「全球可用区（含中国大陆）」→ 绑定自定义域名前必须完成 ICP 备案。

- 选「全球可用区（不含中国大陆）」→ 不要求 ICP 备案。

我一开始以为卡点是「平台要求我先买云资源」。实际卡在别处。 必须有一个境内的接入资源（服务器、云主机这一类），把域名解析过去，由接入商提交，才能备案。

纯静态托管不构成备案所需的接入资源。EdgeOne Pages 只负责把构建产物发出去，它不是我在网站的所有方，也没有替我提交备案的资格。

这也解释了为什么所有教程最后都会绕回买服务器：要备案，先得有接入资源；要有接入资源，先得买服务器。这个过程里不会有哪个页面弹出一句明确的「请先购买云资源」，你只会发现流程走不下去。

为了一个还没验证的想法先付几个月服务器钱，顺序是反的。我停在这里，没有去买机器。

## 这笔账：备案按周算，验证按天算

把两条路径的周期摆在一起，差别就很清楚了。

买服务器备案这条路，时间不花在技术上。实名、准备资料、接入商初审、管局审核，每一段都要等，整体通常是按周计的。再叠加接入资源的前置条件：资源要在你名下，并满足受理时对购买时长的要求，通常是按月计的（具体门槛以受理时的说明为准，我这里不给具体数字）。也就是说，在你还没确认有没有人需要这个产品之前，先要付出一笔以月为单位的预付成本，再加一段以周为单位的等待。

这段时间里，产品可能一次都没有被真实用户打开过。更常见的结局是在等待里把做这件事的热情耗尽，验证还没开始就结束了，而不一定是被备案速度劝退。

反过来先验证，代价是回答来得更早。站点当天就能发出去，一周内就能知道有没有人愿意点开、愿意留下联系方式、愿意聊。这个答案不好看也比没有强，因为它决定了后面那笔钱该不该花。

## 能解决：把加速区域选择好

解决的方式用不到找漏洞。平台本来就提供了这个合法选项：**把项目的加速区域选成「全球可用区（不含中国大陆）」**。

这个区域下添加自定义域名，不要求 ICP 备案。绑定、解析、签发证书，全部走完，站点就挂在自己域名上了。

<img src="/images/edgeone-project-region.webp" alt="EdgeOne Makers 项目概览：加速区域显示为全球可用区（不含中国大陆）" style="max-width:100%;height:auto" width="1360" height="488" loading="lazy" decoding="async">

项目概览页能直接核对三件事：加速区域是「全球可用区（不含中国大陆）」，域名是 `xiaomaker.top`，状态是「运行中」。绑定前先确认区域这一栏，比事后去查备案要求省事得多。

我实际的操作顺序是这样的，供你对照：

1. 账号注册与实名认证时，地区选中国大陆，按流程完成实名。
2. 验证完成后，创建部署项目时，范围选全球（不包含中国大陆区）。
3. 在项目里添加自定义域名，按平台给出的 CNAME 记录去域名商处配置解析。
4. 等证书签发，用手机蜂窝网络确认能打开。

需要说清楚的是，实名和备案是两套东西。**实名是账号层面的身份确认，备案是域名与站点层面的行政许可**。前者我按规矩做了，后者在「不含中国大陆」这个区域下不构成绑定自定义域名的前置条件。这两个概念混在一起，是很多人卡住的原因。

## 具体操作路径与判断依据

按上面的顺序，每一步的判断依据如下。

**第一步：确认站点是纯静态（当然非静态也能部署，稍微麻烦点）。** 能在本地 `npm run build` 出 `dist`，且 `dist` 里不需要额外启动服务，就走得通。如果站点依赖服务端渲染、数据库或定时任务，这条路不适用。

**第二步：把仓库连上平台。** 授权 GitHub 后选仓库。私有仓库同样可以连，授权范围以平台提示为准。

**第三步：填构建参数。** `npm run build`、输出 `dist`、Node 版本与本地一致。构建失败先看日志里第一处报错，通常是 Node 版本不符或依赖没装全，不要一上来怀疑平台。

<img src="/images/edgeone-build-output.webp" alt="EdgeOne 构建产物页：列出 dist 下的 404.html、_astro、images 等输出文件" style="max-width:100%;height:auto" width="1360" height="716" loading="lazy" decoding="async">

产物页看到的是结果：`404.html`、`90-days/`、`_astro/`、`images/` 都在，说明输出目录指对了。反过来，如果这里出现 `src/` 或 `node_modules/`，就是输出目录填错了。构建命令和输出目录这两个字段在项目设置里，产物页不显示，这里能对照的只有结果。

**第四步：用默认域名自测。** 页面能打开、样式正常、图片加载正常，就说明产物没问题。注意默认域名是预览性质、有效期不固定，别拿它当成果。

**第五步：配解析。** 在域名商处按平台给的记录添加 CNAME 指向。域名本身要在注册商处完成实名认证——这是域名管理的要求，不等于 ICP 备案，两者经常被混为一谈。

<img src="/images/dnspod-cname-record.webp" alt="DNSPod 记录列表：一条 TXT 验证记录与一条指向平台接入地址的 CNAME 记录" style="max-width:100%;height:auto" width="1360" height="331" loading="lazy" decoding="async">

我这边有两条记录：TXT 那条用于验证域名归属（值已打码），CNAME 那条才决定流量走到哪里。配置完成后别急着看浏览器，先确认记录本身已经生效。

**第六步：绑定并选对区域。** 这一步是全篇的关键。若流程要求你先提供备案号，先回去看加速区域是不是选了含中国大陆的选项，而不是急着去准备备案材料。

**第七步：验证。** 三件事同时成立才算成功：电脑与手机都能打开、HTTPS 证书正常签发、换一个网络环境（比如蜂窝数据）再试一次仍然能开。很多「打不开」其实是本地 DNS 缓存或只在某个网络下可用，多换环境是最省时间的排查方式。

## 结果与代价

`https://xiaomaker.top` 已经上线，站点是静态的，内容更新靠重新构建。成本结构大致是：域名十多元的年费，加上平台免费版的额度。EdgeOne 免费版的网站安全加速在流量与请求数上不限量；至于构建次数、并发构建、构建时长这类额度细节，以及项目建好后加速区域能否再改，各平台规则会变，**以控制台当时的提示为准，我没有逐一核实，不建议照抄任何具体数字**。

代价必须写清楚，否则这篇就没有意义。

**第一，大陆访问走境外节点，表现是不稳定，而不是稳定地慢。** 有时候是秒开。我截图那次，页面一进去就完整渲染出来，几乎感觉不到等待。其他时候会明显慢，首屏要停一会儿，图片一张张往外冒。到底落在哪一边，跟时段、线路和运营商都有关系，同一个地址今天和明天可以是两种体验。

<img src="/images/edgeone-mobile-quick-open.webp" alt="手机在大陆移动网络下打开 xiaomaker.top，页面完整渲染" style="max-width:100%;height:auto" width="560" height="1244" loading="lazy" decoding="async">

这张截图是运气好的那一次，不是常态。它说明「能打开」是真的，但不说明「每次都这么快」。对图文为主的品牌站，这种波动还能接受；对视频、大图册、交互很重的页面，这种不确定性会被放大成用户流失。

**第二，可达性不是承诺。** 境外节点意味着结果受线路、时段和运营商影响，今天能开不代表下个月一定同样能开。把这种状态当成「正式上线」，需要心里有数。

**第三，这条路有明确的天花板。** 一旦开始收费经营——卖课、卖服务、做交易、收集用户信息——个人备案就不够用。经营性活动需要的是经营性许可，而它必须以备案为前提。到那一步，前面省下的服务器钱和流程时间，都要如实补回去，具体动作写在下一节。

**第四，规则是会变的。** 免费额度、区域是否可切换、默认域名的预览时长、构建环境版本，都属于平台策略，不在我的控制范围内。

## 验证完成之后该做什么

如果验证结果是真的——有人持续在用、有人愿意付钱、你决定长期做下去——接下来的动作是固定的，没有第二种选法：

1. 购买符合备案要求的境内云资源（轻量应用服务器或 CVM 都可以，按备案对购买时长的要求买）。
2. 完成 ICP 备案。
3. 把站点从境外节点迁到大陆节点。

这三步不是可选项，是业务成立之后的必做动作。原因很直接：大陆节点决定体验，备案决定这门生意能不能公开见人。前面那套临时方案只解决一件事——在还没验证之前，不必先付这笔钱、先等这段时间。

也要接受一个落差：迁移不是零成本。重新配置构建与域名、重新验证收录、可能还要重新提交备案材料，都要再走一遍，中间站点可能短暂不可用或换地址。这些应该提前算进计划，而不是做到一半才发现。

## 什么时候这条路不该走

下面几种情况，我认为不值得绕：

- 目标用户几乎全在大陆，且对打开速度敏感。省下的钱会变成持续的用户流失。

- 站点要处理登录、支付、个人信息。合规要求不是技术能绕开的。

- 你预期三个月内就会进入收费环节。那就直接按经营性的路径准备，不要先走捷径再回头补。

反过来，如果站点是纯展示、主要目的是「让想看的人能看到、让想联系我的人能找到我」，并且你正在验证一个还没被市场确认的想法，那这条路是合适的：用最小的固定成本，把一个东西真实地放到公网上，让真实的反馈进来。

## 我最后得到的判断

省下一台服务器只是附带结果。这次真正的收获是把两件事分开：**技术可达性可以优化，行政合规不能跳过。**

不买服务器、不备案，能上线。但它是「先验证、后补票」的状态，不是终态。验证阶段用它当临时脚手架没问题；真要长期用，迟早会在某一个环节被堵住。

对我来说，这一步的价值在于：我可以在很低的固定成本下，让一个想法被真实的人看到。至于要不要为它去买服务器、去备案，应该由验证结果来决定，而不是由建站的第一步决定。
